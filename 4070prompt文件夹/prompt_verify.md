# 代码完成后发给服务器 AI 的验证提示词

以下全文可直接发给编码 AI，也可以交给另一个验证 AI。须让它读取实际代码和运行产物，不只读取编码 AI 的总结。

---

请验证当前服务器上的球形机器人导航 baseline 与已知地图采集实现。先阅读本交接包 `design.md`、`implementation_plan.md`，再阅读实际 Git diff、实现报告、配置、测试和日志。你的任务是发现真实问题、复现、做局部修复并复测，而不是为已有实现写通过证明。

不要只给测试建议，请实际执行当前环境允许的检查。不要重写整个系统，不偷偷降低安全裕度、扩大目标半径、延长预算、关闭接触或放宽断言。保持旧数据和日志，所有新运行写到唯一目录。

## 1. 先建立可复核基线

记录当前 commit、dirty diff hash、Python/Isaac launcher、Torch/CUDA、GPU、模型配置与 checkpoint SHA256、机器人/场景资产、配置 hash。核对实现者所称“通过”的日志是否来自本次代码与配置。旧分支、旧权重、旧结果不能替代当前验证。

以 `PASS / FAIL / BLOCKED / NOT_RUN` 标记每项：

- `PASS`：实际执行且满足固定条件。
- `FAIL`：实际执行不满足，或本应交付的接口未实现。
- `BLOCKED`：环境/依赖/资产缺失，无法执行；必须说明已尝试的命令和具体缺项。
- `NOT_RUN`：未执行，说明原因。skip 不自动算 PASS。

把“软件正确”“真实链路运行”“导航效果”“实时能力”“数据可训练”分别判断。smoke 通过、程序退出码 0、生成视频，都不等于无碰撞到达。

## 2. 先审查代码中最危险的路径

逐项检查并指出真实文件、函数和行号：

1. 视觉策略能否通过 runtime、闭包、缓存、文件路径或全局对象读完整地图、Oracle 路径、未来帧、未来状态？估计位姿是否暗中由真值填充？truth 记录器是否与 online 共享可变对象？
2. 左右是否独立估深？DA3 实际模型/权重是什么？米制转换是否漏做或重复做？高级 API 输出和低层原始输出有没有混用？
3. renderer 深度为 z 还是 range？相机旋转/裁剪/缩放是否更新 K 和 mask？wxyz/xyzw、T 的方向、m/cm、rad/deg、地图行列是否一致？
4. 深度是否按源 frame ID 和采集姿态配准？过期、乱序、跨 episode 和只 shape 相同的结果是否会被接受？render 是否额外推进物理？
5. NaN/Inf/零深度、遮挡、孔洞、超距输出是否被当成最大深度清空地图？地面三角片是否跨越深度断边或矮箱？只检测障碍、没有自由证据是否导致启动死锁？
6. 足迹是否漏算或膨胀两次？是否强制把起点及邻近未知改为可走？是否只检查轨迹中心而忽略扫掠体积？
7. 局部参考终点是否误作全局目标？是否用未经验证的原地转向？零请求是否误记成物理停稳？请求、协议、PID/平滑和 applied 是否被同一数组覆盖？
8. writer、audit、resume、split 是否真实起作用？异常退出有没有伪造 timeout/success？半截数据、重复 episode 或不同版本缓存是否进入正式 manifest？

代码审查只能发现嫌疑；关键来源/坐标/时间错误还要用后续测试证实。

## 3. CPU 合同和故障注入测试

查找实际测试入口，不把交接包示例命令当成已经存在。先执行新增测试和相关旧回归，记录收集/通过/失败/跳过数量。若漏测以下关键行为，增加小型独立 fixture 后运行：

| 测试 | 固定输入/扰动 | 必须出现的行为 |
|---|---|---|
| 针孔投影 | fx=fy=100,cx=cy=1，像素(2,1)，z=2 | 点为(0.02,0,2)，再用已知 T 手算世界点一致 |
| range/z 区分 | 同一斜向像素的 ray distance | 转为 z 后投影一致，直接用 range 的错误实现被抓到 |
| 图像变换 | 缩放、裁剪、90°旋转 | 恢复后同一三维点一致，mask 不偏移 |
| 姿态补偿 | 同一世界平面在两种 roll/pitch 下 | 回投平面一致，不能在倾侧时凭空出现障碍 |
| 单位转换 | fake raw 输出与 fake 已米制输出分别测试 | 低层仅缩放一次，高级 API 不二次缩放 |
| 无效观测 | 全 mask、全 NaN、零、Inf、负值、单侧缺失 | 不清空障碍、不创建自由格，按配置制动或显式降级 |
| 观测配准 | frame/episode/camera ID 错，乱序时间 | 拒绝，记录具体原因，不进入地图 |
| 三态融合 | 同格旧自由/新占据、左右冲突、过期障碍 | 可信占据优先；过期最多回未知 |
| 连续地面 | 已观测平地＋孔洞＋矮箱 | 充分观测空地可连接；不跨洞、不清掉箱体 |
| 足迹 | 窄通道、足够宽通道、对角墙角 | 窄的拒绝、宽的通过、不切角、无重复膨胀 |
| 权限 | guard provider；同 online 输入替换 hidden map | 非法读访问报错，策略不随隐藏地图变化 |
| 临时子目标 | 到达 frontier 但距最终目标仍远 | 不标全局成功，重新观测/规划 |
| 动作时间 | 10Hz 两段转移，50Hz 10个不同动作 | 每段恰关联随后5个动作，无一拍偏移 |
| 动作层 | 四层设置不同值并复用原数组 | 落盘值独立，后续数组修改不污染旧行 |
| 评分 | 同步接触与到达、地面接触、进程异常 | 无碰撞成功不能覆盖有效障碍接触；地面不误报；异常不伪成功 |
| 通道资格 | 参考经过、实际轨迹绕过门线 | corridor_passed=false，即使最终到达也分开报告 |
| 中断与恢复 | finalize 前抛异常、完整episode重跑、改hash | incomplete不入manifest；不重复；不同版本拒绝复用 |
| 数据篡改 | 缺图、坏文件、错hash、跨split同context | strict audit 非零退出并定位具体记录 |

如果宣称实现异步，再测队列有界、worker 崩溃、旧结果、未来时间、跨 episode reset；如果只实现 lockstep，标异步未实现，不因此把基础范围判失败。

预期数值误差容差根据 dtype 和计算步骤事先固定。不能看到误差后不断放大容差。测试真实行为，不只是测试某个函数能被 mock 调用。

## 4. 真实 GPU 深度检查

1. 真实严格加载所声明 checkpoint，先一对图确认 RGB/标定/输出单位和 shape；预热单独记录。
2. 至少 30 对稳态图测左右一对耗时 p50/p95、显存峰值；再在 Isaac 并发时测量或明确未测并发。
3. 用覆盖静止、前进、倾侧、转弯、近障、自体遮挡的 100–300 对开发帧，核对 RGB/GT/预测/mask/时间一致。
4. 按眼别、距离、障碍/地面、边缘和运动状态分组，报告有效覆盖、误差分位数、障碍漏检和虚假障碍。所有关键障碍区域进分母，无效输出计入漏检并单列。
5. 禁止逐帧真值尺度对齐后声称模型可直接导航；禁止只展示最好看的 3 张图。抽查至少 5 个不同条件帧，包括最差近障例子。
6. 核对 `acceptance_profile.json` 的工作区间、margin、停止距离和参数来源。未冻结或缺数据时，判定性能资格未建立，不自行编造通过阈值。

精度不够应报告模型/场景适配问题。10Hz 推理不达标应如实报告，不能把仿真暂停的 lockstep 说成实时。无 GPU 或权重只能 BLOCKED，CPU fake 不能替代本节。

## 5. 真实 Isaac 闭环检查

先执行一条 5–10 s 短 smoke，确认物理步、图像更新、关节真实响应、接触流和记录器工作。失败先查具体层，不继续烧大量任务。

随后冻结任务、配置和代码，执行 E0/E1/E2 × 下列三模式，共 9 个完整 episode：

- known_map_gt_pose
- visible_gt_depth_gt_pose
- dual_mono_gt_pose

若已有同一当前版本、同配置并可审计的完整运行可以复用，但抽查其一致性；版本、模型或关键配置变更后必须重跑受影响任务。估计定位完成时再单独追加三条。

主表沿用核验后的 35 s、0.20 m 和 50Hz 真实障碍接触规则。不为提高成功率修改这些条件。新增长预算或停稳任务单独出表。

额外做一条有意真实障碍接触、一条不可达任务，只验证判据，不计入成功率。确认过滤地面后真实接触能触发；渲染网格和碰撞体对齐；不能只用几何距离或文件里的 collision 标志模拟物理检测。

每条输出至少：模式、任务、seed、到达/碰撞/超时/异常、仿真/墙钟时间、路径长度、剩余距离、首次接触时间、实际速度、重规划数、深度年龄/覆盖、原因和日志路径。

对 E1 确认直线受阻且有可行绕行；对 E2 检查实际轨迹按门线序列通过通道，不是仅参考路线经过。抽查至少 3 条任务的起点、转弯、近障和终止叠图与视频。

软件可运行但 9 条都停车超时，不能判视觉 baseline 已可用。至少检查 E0 已知地图和可见真值深度各有一条无碰撞到达；否则输出起点连通性、足迹净空、执行响应等诊断，先修这些问题。E1/E2/DA3 效果不承诺，失败要保留并说明，不通过假成功掩盖。

## 6. 真实数据集检查

在新目录试采总计 20–30 条 episode，或核对已存在的同版本试采。布局 split 必须先冻结。执行真实 strict audit 并抽查至少 3 条，不能只检查文件数量。

必须检查：

- 左右原始 RGB 能解码、确为本条轨迹，不是上次缓存或复制帧；静止画面相同本身不算错误，但 frame/time 必须更新。
- 50Hz 控制/状态与 10Hz 图像的时间、shape、单位和转移区间正确；终止不完整区间有明确 mask。
- raw/protocol/PID平滑/applied 与真实关节反馈分开，动作幅度、控制状态及时间对得上。
- GT 深度、预测深度、完整地图标签与观察 mask 明确区分；训练 online loader 白名单不读取 truth。
- COMPLETE、manifest、hash、配置、commit、checkpoint、scene/layout/context/split 一致，没有半截或重复 episode。
- scene/layout group 不跨 split，不能把同几何换纹理称为未见布局。
- 实际中断一次当前测试采集进程并 resume，确认只跳过完整且同版本 episode，未完成的从初态重采且旧诊断保留。只中断自己启动的进程，不影响其他 GPU/服务器任务。
- 成功、碰撞、超时和异常退出没有混淆；保留失败记录，不让训练索引偷偷筛成只有成功但报告仍称全量。

如果实现动作分支，另查完整上下文恢复或前缀重放、控制器状态、重复 rollout 误差与分支同组划分。只恢复 root pose 则该功能 FAIL，不能作为正式候选排序数据；普通轨迹数据可以独立通过。

## 7. 修复与复测规则

发现错误后先保留失败证据，补能复现它的针对性检查，再做最小修复。修完复跑失败检查和受影响回归；凡改变深度、标定、地图、控制、评分、数据语义的修复，重跑受影响真实任务和 audit。

不要通过删除难任务、过滤无效像素分母、跳过碰撞、修改目标半径、放宽 split、关掉 strict audit 或静默 fallback 解决失败。性能问题与逻辑错误分开：若导航失败来自深度能力或观测不足，交付明确结论和复现，不无限扫参数直到开发任务偶然成功。

## 8. 请提交这些结果

生成：

1. `reports/navigation_baseline/verification_report.md`：逐阶段结果、发现、修复、证据、限制和真实复现命令。
2. `verification_results.json`：机器可读检查清单。
3. `failed_cases.csv`：逐失败任务和复现信息，空表也保留表头。
4. CPU 测试日志、真实 GPU/Isaac 日志、任务逐行结果、strict audit 输出、少量叠图/视频和样本 manifest 的路径索引。

JSON 建议结构如下，示例状态不是实际测试结果，不可原样当结论：

```json
{
  "code_commit": "actual_commit",
  "dirty_diff_sha256": "actual_hash_or_clean",
  "config_sha256": "actual_hash",
  "checks": [
    {
      "id": "geometry_projection",
      "status": "NOT_RUN",
      "command": null,
      "exit_code": null,
      "evidence": [],
      "reason": "示例记录，执行后填写"
    }
  ],
  "readiness": {
    "known_map_collection": "NOT_RUN",
    "visible_depth_navigation": "NOT_RUN",
    "dual_mono_navigation": "NOT_RUN",
    "estimated_pose_navigation": "NOT_RUN",
    "branch_rollouts": "NOT_RUN",
    "realtime": "NOT_RUN"
  }
}
```

CSV 至少含 `episode_id,mode,scene,seed,status,failure_layer,reason,reproduce_command,evidence_path`。路径为实际存在的文件；结论和汇总表都从本次原始记录生成，不手填成功率。

最后用简短中文回答：

- 已知地图数据采集能否使用，数据是否通过审计？
- 可见真值深度版本是否能正常启动和导航？
- DA3 视觉版本是已无碰撞到达、仅接通但效果不足，还是尚未实测？
- 有没有真值泄漏、坐标/时间错配、碰撞漏判、数据污染等硬错误？
- 哪些检查没跑，哪些问题仍在，下一步只需优先解决什么？

请给真实结果，允许结论是部分可用或性能不达标。不要只说“所有测试通过”而不列检查范围和证据。
